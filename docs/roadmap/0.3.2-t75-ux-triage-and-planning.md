# T75 — 0.3.2 UX findings triage and next-version planning

날짜: 2026-10-14. 기준: `main` = `next` = `5d33783`, npm `latest` 0.3.2. 감사와 계획만 했다. 제품 코드·version·tag·Release·External Validation 01(정확히 0.2.1)은 바꾸지 않았고 Issue를 닫지 않았다. 실험은 maintainer 쪽 Agent의 자체 측정이며 외부 사용자 결과가 아니다.

## 1. 요약

- **#8의 원인을 실험으로 확인했다.** 같은 tool 목록을 내는 stub MCP server로 시험했다. 지연이 없으면 Codex가 tool을 6/6 찾았고, 1.2초 지연이면 3/4, 1.8초 지연이면 0/4, 2.5초 지연이면 0/6이었다. 실제 DUO server의 시작은 단독 0.87~1.48초, 8개 동시 시작 1.8~3.2초다. 따라서 발견 실패가 시작되는 경계(약 1.0~1.2초)에 DUO의 평소 시작 시간이 걸쳐 있다. 같은 2.5초 지연에서도 bridge에 "처음에 없으면 몇 초 뒤 다시 확인" 한 줄을 넣자 4/4 찾았다. 시작 시간 단축과 재확인 안내는 각각 효과가 있다. 원인 중 "목록을 세션 초반에 한 번 보는" 부분은 Codex 쪽 동작이다.
- **constraint 문제의 원인은 계약과 init 사이의 틈이다.** 계약(ADR-007 C107, H-33)은 constraint를 결정적 검사가 아니라 context·relevance·의미 판정 입력으로 정했다. 관련성은 constraint의 `match`로만 판정한다. 그런데 init은 `match` 없는 constraint를 confirmed, `enforcement: warn`으로 쓴다. 그래서 init constraint는 어떤 context와 review에도 나타나지 않는다. 요구사항 문서(01 §285)와 README 문구는 검사되는 것처럼 읽힌다.
- **0.3.3 후보는 계약을 바꾸지 않는 다섯 가지다.** MCP 시작 단축, bridge 재확인 한 줄, constraint의 의미를 드러내는 문구·가시성, `--answers` 오류, 사람용 근거 줄이다. 동작·정책 변경(constraint를 context에 싣기, constraint → Decision 경로, #7, #4, 한 명령 설정)은 0.4로 둔다.
- **PR #13**: 과장되거나 증거가 부족한 표현 다섯 곳을 고쳤다(`db3384d`). 문서만 바뀌며 merge 가능하다고 평가한다. 자동 merge는 하지 않았다.

### 3.2 인과 실험

같은 저장소 사본에 `[mcp_servers.duo-director]`를 바꿔 끼웠다. stub(`stub.cjs`)은 DUO의 tool 9개와 같은 이름·제목·설명·입력 schema를 내고 짧은 text로 답한다. 지정한 시간만큼 initialize에 늦게 답하고, 시작·initialize·tools/list·첫 호출 시각을 log로 남긴다. prompt는 "50달러 이상 주문 page를 계획만(파일 변경 금지)"이다. Codex 0.147.0, 사용자 설정 사본(model `anthropic/claude-opus-5-5`, code mode). 조건을 번갈아 한 번에 하나씩 실행했다.

| S12 stub, 1.2초 | **3/4** | |
| S18 stub, 1.8초 | **0/4** | 모두 CLI fallback |
| S25 stub, 2.5초 | **0/6** | 모두 CLI fallback, 대부분 "not exposed" 언급 |

재확인 한 줄: "If the duo_* tools are not in your tool list when the session starts, wait a few seconds and check the list again before you fall back: the duo-director server can take a few seconds to start."

해석과 한계:

- Codex(이 구성)는 세션 초반의 tool 목록으로 판단한다. server가 약 1.2초 안에 답하지 않으면 그 세션에서 DUO tool을 쓰지 않을 가능성이 높다. T74의 4/8 실패는 부하로 시작이 늦어진 실행과 맞는다.
- "목록을 한 번만 본다"는 Codex 쪽 동작이다. DUO가 고칠 수 있는 것은 자기 시작 시간과 안내 문구다.
- 표본이 작다(조건당 4~6회, prompt 1종, 구성 1개, OS 1개). 다른 Codex 구성과 Claude Code는 측정하지 않았다. Claude Code는 init event에서 연결과 9 tools를 확인했으므로, 세션 시작 전에 연결을 기다리는 것으로 보이지만 실제 Agent 작업은 검증하지 않았다(계정 미로그인).

## 4. Critical constraints 신뢰성

### 4.1 현재 계약

- ADR-007 R-CONSTRAINT 해석 변경(C107, H-33): "MVP에서 Constraint는 Context, relevance, 의미 판정의 입력이고, 결정적 차단은 confirmed Decision의 명시적 `forbids` + `enforcement: block`으로만 한다. Constraint schema에 forbids나 enforcement DSL을 두지 않으며, 필요가 확인되면 별도 ADR로 확장한다."
- 05-context-compiler: confirmed Constraint는 `matchConstraint`가 `none`이 아닐 때만 CONFIRMED INTENT에 들어간다.
- review `constraint-compliance`: `match`가 맞는 confirmed constraint에 UNKNOWN 의미 후보 claim만 만든다.
- 03-data-model: init의 `constraints.yaml`은 "Human이 준 것만 confirmed, enforcement warn"이다. `match`는 쓰지 않는다.

### 4.2 PASS가 나오는 원인

`matchConstraint`는 `match.paths`·`match.symbols`·`match.keywords`로만 관련성을 정한다. init constraint에는 셋 다 없어 언제나 `none`이다. 결과적으로 init constraint는 context packet, review claim, Knowledge Gap 어디에도 쓰이지 않는다. `enforcement` 값은 어떤 판정에도 영향을 주지 않는다. 남는 곳은 `status`·`doctor`의 개수와 MCP `duo_search_evidence`·`duo_get_decision` 검색뿐이다. 문서는 서로 어긋난다. 01-requirements §285는 "명백한 Constraint와 Decision 위반은 규칙으로 판정한다"고, README는 Project Truth를 "the reference every review uses"라고 한다.

### 4.3 의미와 책임 (제안)

| | Decision | Constraint |
|---|---|---|
| 의미 | 사람이 확정한 공학적 선택(질문과 답) | 사람이 확정한 한계나 의도의 진술 |
| 결정적 검사 | `forbids` + `enforcement`가 있으면 review가 diff를 검사(BLOCK·WARN) | 없음(C107) |
| 쓰이는 곳 | context, review, lock, supersede | `match`가 있을 때 context와 의미 후보, 없으면 기록만 |
| 만드는 길 | Agent proposal → 사람 확정(대화형) | init 질문 또는 파일 직접 편집 |

### 4.4 선택지

| ID | 내용 | 사용자 가치 | 호환성 | 회귀 위험 | SemVer |
|---|---|---|---|---|---|
| C-A | 문구만: init 질문·요약, README 핵심 개념, 01 §285를 계약에 맞춤 | 오해 감소(읽는 사람만) | 동작 동일 | 낮음 | patch |
| C-B | C-A + 가시성: review에 additive limitation(예: `constraints-unscoped`, `match` 없는 confirmed constraint 목록), doctor·status에 "N개는 context와 review에 쓰이지 않음", init은 한 줄에 하나씩 입력(`;` 분할 폐지, answers JSON 형식 그대로) | 조용한 미검사가 매번 보임 | verdict·claim 불변, `/1`에 limitation 코드 추가(0.3.1의 additive 선례) | 낮음~중간(출력 줄 증가, 문서 예시·conformance) | patch |

권고: 0.3.3에 **C-B**(C-A 포함), 0.4에 C-C와 C-D를 함께 설계한다. 어떤 선택지도 Decision을 자동으로 만들거나 확정하지 않는다.

C-B acceptance criteria: init constraint만 있는 저장소의 review·`--json`에 해당 limitation과 constraint ID가 보이고 verdict는 그대로다. doctor·status에 미사용 개수가 나온다. init TTY에서 한 줄씩 입력받고, answers JSON은 그대로 받는다. `match`가 있는 constraint의 기존 동작은 byte 동일하다. 01 §285·README 문구가 ADR-007과 일치한다.
