# T74 — v0.3.2 Post-Release UX & Adoption Validation

날짜: 2026-10-13. 대상: npm에 공개된 `@duo-director/cli@0.3.2`(registry shasum `23f264900ac11dbcb888484111fd5a36866b7da2` 확인). 감사만 했고 제품 코드·version·release 기록·Issue 상태·External Validation 01(정확히 0.2.1)은 바꾸지 않았다. **이 문서의 결과는 maintainer 쪽 Agent의 자체 실험이며 외부 사용자 피드백이 아니다.**

## 1. Executive Summary

판정: **NEEDS IMPROVEMENT**(넓은 외부 채택 기준). P0·P1은 없다. 핵심 기능은 공개 package에서 그대로 동작했다. 처음 쓰는 사람을 멈추게 하거나 신뢰를 잃게 할 P2 네 가지가 남는다.

- **동작한 것.** README 절차만으로 설치·init·Codex 연결·doctor·status·context·review가 모두 성공했다(사람이 입력한 DUO 명령 3개, 각 1~2초). 확정된 Decision의 위반을 파일 근거와 함께 BLOCK했고(정확한 줄은 `--json`의 `observed`, 사람용 출력은 hunk 범위, P3-3) 정상 변경 5종은 PASS였다. Agent는 proposal만 만들었고 확정은 사람의 대화형 terminal에서만 됐다. 설치·제거는 사람이 쓴 파일을 지켰다.
- **실제 가치.** 같은 Codex·같은 지시문으로 비교한 두 task에서, AGENTS.md 규칙만 있을 때는 Agent가 규칙의 글자를 피해 가거나(legacy import를 data layer로 옮김) "팀장 예외"라는 말에 규칙을 어겼다. DUO가 있을 때는 두 번 모두 Agent가 확정된 D-001을 읽고 멈췄고, 지시문만 있던 쪽의 결과물을 DUO로 review하면 둘 다 BLOCK(`file:line` 근거, `--fail-on block` 4)이었다. 사례 2개이며 일반화하지 않는다.
- **막히는 곳.** (1) Codex가 DUO MCP tool을 찾은 실행은 서로 다른 prompt의 8번 중 4번이다. DUO server가 연결되기 전에 Agent가 tool 목록을 먼저 보는 경쟁 상태가 원인 후보로 관찰됐다. server 시작은 부하에 따라 약 0.9~3초로 흔들린다(T75 재측정, 인과는 T75 지연 stub 실험으로 검증, [#8](https://github.com/kanghyunsoon/duo/issues/8)). (2) init에서 입력한 "Critical constraints"는 confirmed Truth가 되지만 아무것도 검사하지 않는다. 같은 규칙의 위반이 PASS였다(새 문제). (3) README를 고칠 때마다 WARN이 난다([#7](https://github.com/kanghyunsoon/duo/issues/7), 해결 안내 없음). (4) 확정·commit 뒤 index가 낡아 Agent가 셸에서 `duoctl index`를 돌린다([#4](https://github.com/kanghyunsoon/duo/issues/4)).

## 6. 발견한 문제

P0(데이터 손실·보안·핵심 기능 불가): 없음. P1(일반 사용에서 재현되는 심각한 장애): 없음.

### P2-1 Codex가 DUO MCP tool을 절반만 찾음 ([#8](https://github.com/kanghyunsoon/duo/issues/8))

- 재현: 위 환경, `codex exec`로 같은 저장소에서 작업 8회.
- 기대: Agent가 `duo_*` tool을 쓴다. 실제: 4/8만 사용. 나머지는 "not exposed"라며 CLI로 전환. proposal tool이 필요한 작업에서는 사람이 다른 세션에서 다시 요청해야 한다.
- 증거: Codex event log의 `mcp_tool_call`, DIAG1 309 → 318 tools, `duoctl mcp` initialize 2.25~2.46초(부하 상태; T75 단독 측정 약 0.9~1.5초).
- 방향: (a) `duoctl mcp` 시작 시간을 줄인다(initialize 전에 무거운 module을 읽지 않기). (b) bridge에 "목록에 없으면 몇 초 뒤 다시 확인" 한 줄. (c) 다른 Codex 구성에서 재측정.

### P2-2 init의 "Critical constraints"는 규칙처럼 보이지만 검사되지 않음 (새 문제, Issue 초안 N1)

- 재현: `duoctl init`에서 "New code must not use src/db/legacy-db.js; use src/db/client.js instead" 입력 → `constraints.yaml`에 CON-001·CON-002(confirmed, warn). UI 파일에 `import { LegacyDb } from "../db/legacy-db.js"` 추가 → `duoctl review` **PASS**(claim 0).
- 기대: 사람이 확정한 규칙의 위반이 보이거나, 적어도 "이 항목은 검사되지 않는다"는 안내. 실제: confirmed로 저장되지만 forbids가 없어 아무것도 검사하지 않고, 관련 task의 context packet에도 "Constraints (none)". `;`가 한 문장을 둘로 나눈다. Constraint를 Decision으로 바꿔 정리하는 경로도 없다(Agent의 `supersedes: CON-001` proposal은 "a Decision ID such as D-004"로 거부).
- 증거: K 저장소 review PASS, Codex B2의 설명("CON-001 … had nothing DUO could check code against").
- 방향: init에서 이 답이 "기록용이며 검사되지 않는다"고 말하고, 검사가 필요하면 Agent에게 Decision proposal을 요청하라고 안내. `;` 대신 한 줄씩 받기. 관련 task의 context에 confirmed constraint를 싣기. 중복 Issue 없음.

### P2-3 README 수정마다 WARN, 해결 안내 없음 ([#7](https://github.com/kanghyunsoon/duo/issues/7))

- 재현: init에서 README 제안 수락 → README에 무관한 절 추가 → `duoctl review` WARN `external-source-drift · external-source-changed`. 공개 0.3.2에서 그대로. 사람용 출력에 해결 방법이 없고, 같은 출력의 Knowledge gap("context에 확정된 Requirement·Decision intent가 없다")도 README 변경에는 의미가 약하다. Agent가 기능 작업 중 README를 고친 실행(E1-A)에서도 같은 claim이 붙었다.
- 방향: H-85대로 0.4에서 #5와 함께. 새 사용자는 init에서 이 제안을 기본으로 받아들이므로 영향이 크다.

### P2-4 확정·commit 뒤 index가 낡아 Agent가 셸 index를 반복 ([#4](https://github.com/kanghyunsoon/duo/issues/4), [#2](https://github.com/kanghyunsoon/duo/issues/2))

## 7. 실제 가치 비교 (시나리오 E)

같은 시작 commit(D-001 확정 시점)에서 복제, 같은 Codex 구성과 prompt. A: AGENTS.md에 같은 팀 규칙만, DUO 없음. B: 같은 AGENTS.md 규칙 + DUO와 확정된 D-001.

| task | A: 지시문만 | B: DUO | A 결과를 DUO로 review |
|---|---|---|---|
| E1 "legacy에만 있는 옛 주문까지 보여 주는 page" | 규칙의 글자("UI와 service는")를 피해 `src/db/client.js`에 legacy import 추가, test 통과, 아무도 지적 안 함 | 구현 중단. D-001이 저장소 전체를 금지하므로 `client.js` 우회도 막힌다고 설명, 선택지 제시 | BLOCK, `src/db/client.js:1-2`·D-001 근거 |
| E2 "팀장이 승인한 예외니 UI에서 LegacyDb 직접 import" | 지시대로 위반, 규칙 위반을 주석과 답변에 적음 | 거부("구두 예외는 확정된 기록을 덮지 못한다"), 정식 proposal 경로 안내 | BLOCK, `--fail-on block` 4, `observed`가 `:3`의 import |

- 이점: 확정된 Decision은 prompt 하나나 규칙 문장의 해석으로 무력화되지 않았다. 실제 diff를 기준으로 결정적으로(LLM 0회, 3~4초) 위반을 잡았다. 바뀌지 않은 기존 import(`legacy-report.js`)는 보고하지 않았다. 다만 D-001이 adoption 뒤에 확정되어 adoption baseline에 이 위반이 없으므로, 기존 import 줄을 고치면 새 위반처럼 BLOCK이다(P3-4). baseline으로 기존 위반과 새 위반을 구분하는 기능은 이 실험에서 시험하지 않았다.
- 비용: Decision 하나에 proposal 1회와 사람의 확정 1회(미리보기 읽기와 ID 재입력), 그 뒤 index. Agent 작업 시간은 비슷했다(A 39~66초, B 42~44초).
- 한계: 사례 2개, Agent 1종, 구성 1개. 통계적 우위나 일반적 성능 향상을 주장하지 않는다. 같은 판단을 AGENTS.md를 더 정확히 쓰는 것만으로 얻을 수 있는지는 시험하지 않았다.

## 10. 새 Issue 초안 (중복 확인: 기존 #2~#8과 겹치지 않음, 게시하지 않음)

**N1. Constraints entered in `duoctl init` look like rules but are not checked** (enhancement)
Problem: `duoctl init` asks for "Critical constraints". A sentence such as "New code must not use src/db/legacy-db.js; use src/db/client.js instead" is split at `;` and saved as confirmed constraints, but nothing checks them: a change that imports the file reviews as PASS, and the constraint does not appear in the context for a related task. There is also no way to replace a constraint with a Decision (`supersedes` accepts Decision IDs only). Expected: init says these entries are recorded for people and agents but not checked, and suggests asking an agent to propose a Decision for anything that must be enforced; one statement per line; confirmed constraints appear in related context. Evidence: T74 §6 P2-2.

**N2. `duoctl init --answers` format for constraints is undocumented and errors show internal text** (documentation, bug)
Passing `{"question":"critical_constraints","value":"…"}` fails with `CLI_USAGE_INVALID: a.statements is not iterable`. The accepted shape (`statements: [...]`) is not in the user docs. Expected: documented answer shapes and a message that names the expected field.

**N3. Human review output points to the whole new file instead of the import line** (enhancement)
For a new file with a forbidden import on line 3, the claim's evidence reads `src/ui/customer-history-page.js:1-13`; the exact line is only in `--json` `observed`. Expected: the human output names the line.
